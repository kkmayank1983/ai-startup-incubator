Session Mission

In this lab, you will perform a professional Refactoring of your Personal AI. You will transition from a single messy script to a Three-Tier Architecture: Config, Brain, and Interface.

1. The Architect's Pivot: Refactoring

The Reality Check: Up until now, you were "Scripting"—writing quick lines to test ideas. But as a Co-founder, you must now move to "Engineering."

When code gets complex, we use Refactoring. This means rewriting the internal structure of your code without changing its external behavior. Why do we do this?

  • Maintainability: Making it easy to find and fix bugs.
  • Scalability: Adding new features without the system collapsing.
  • Separation of Concerns: Ensuring each file has only one specific job.

THE BLUEPRINT

We are splitting your system into three distinct modules:

  1. config.py: The "Vault." Handles API keys and model settings.
  2. brain.py: The "Logic Engine." Handles persona and memory.
  3. app.py: The "Entry Point." The file you run to launch the interface.

This design creates "abstraction layers". Each module hides its internal complexity and exposes only the functionality the rest of the system needs.

2. Visualizing the Architecture

How the modules connect:

[ USER INPUT ]
  ↓
app.py (The Captain)
  ↳ asks config.py for the model settings

[ AI OUTPUT ]

Today you built the first three layers of that architecture.

3. Module 1: config.py (The Environment)

This module acts as the "Vault" for your system. Its only job is to manage the settings and API connections that allow your code to talk to the AI Cloud. By putting your load_dotenv() and llm initialization here, you create a central command center.

Why use it? If you decide to switch from GPT-4o-mini to a different model, or if you want to turn down the "Temperature" for the whole project, you only have to change one line in this file instead of hunting through hundreds of lines of code.

Reasoning Step: If you want to change your model temperature or API key, how many files should you have to edit? In a modular system, the answer is always one.

4. Module 2: brain.py (Logic & Memory)

This module is where the "Thinking Process" of your AI lives. It encapsulates the Persona Rules (Session 3) and the Memory Notebook (Session 4). It creates the initialize_system() function, which builds the AI object that the rest of the application will use.

"""
AI Brain Architecture:   User Input
   ↓
  System Rules (Persona) + input + LLM
   ↓
  Memory Updates
   ↓
  Response Generation
"""


Why use it? Professional engineers hide the "messy" AI logic inside this module so the main app doesn't have to see it. This makes it much easier to add advanced features, like structured output or special tools, without breaking the part of the code that talks to the user.

Reasoning Step: Does the User Interface need to know how memory is saved? No. That is a "Concern" that only the Brain should handle.

🛠 Activity: Encapsulating the Brain

  1. Create a new file named brain.py.
  2. We wrap our personality and memory tools inside a reusable function.

brain.py
from langchain_classic.chains import ConversationChain
from langchain_classic.memory import ConversationBufferMemory
from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

def initialize_system(llm):
    """
    Sets up the Personality Rules 
    and Memory Notebook 
    """

    # --- Persona Rules  ---
    system_rules = """
    You are a helpful Personal AI assistant.
    Always respond clearly and concisely.
    """

    prompt = ChatPromptTemplate.from_messages([
    ("system", system_rules),
    MessagesPlaceholder(variable_name="history"),
    ("human", "{input}")
])
    

    # --- Memory Notebook  ---
    memory = ConversationBufferMemory(
    memory_key="history",
    return_messages=True
)
    # --- Create the AI Brain ---
    bot = ConversationChain(
        llm=llm,
        memory=memory,
        prompt=prompt,
        verbose=False
    )

    return bot

Verification: You won’t see output yet—but this file now defines HOW your AI thinks and remembers.

5. Module 3: app.py (The Entry Point)

This module is the "Captain" of your system. It is the file you actually run to launch your Personal LLM. Its job is to handle the User Interface (UI), which in our case is the terminal loop where the user types. It coordinates between the Config and the Brain to deliver the final response.
When you run: python app.py Python begins executing code from this file first. That is why we call it the "Entry Point".

Why use it? By keeping the "Interface" separate from the "Logic," you make your system flexible. In the future, you could replace this terminal loop with a website or a voice interface, and you wouldn't have to change a single line of code in your Brain or Config modules!

The Entry Point is the file that launches the system. It coordinates the Config and the Brain like a conductor leads an orchestra.

⚙ Troubleshooting & FAQs

❓ ModuleNotFoundError: No module named 'config' or 'brain'

This is the most common modular error. Check the following:

  • Ensure config.py, brain.py, and app.py are all in the exact same folder.
  • Check for typos in your filenames. If you named it configs.py but imported config, it will fail.
  • Make sure you saved all files (Ctrl + S) before running app.py.

❓ AttributeError: 'NoneType' object has no attribute 'predict'

This happens if your initialize_system function in brain.py doesn't actually "give back" the bot.

The Fix: Ensure the very last line of that function is return bot. If you forget to return, the variable in app.py stays empty (None).

❓ I changed the rules in brain.py but nothing happened

Since app.py imports the logic, it needs to be restarted to see the new changes.

The Fix: Stop your terminal (Ctrl + C) and run python app.py again to load the updated rules.

❓ ImportError: cannot import name 'llm'

This happens if you named the variable something else in config.py.

The Fix: Check config.py. If you wrote my_llm = ChatOpenAI(...), then in app.py you must use from config import my_llm.
