Session 2: The Tokenization & Preprocessing Pipeline

Language models cannot see letters. They see numerical sequences. Today, you engineer the gateway between the human world and the math world.

60 Minutes Level: Junior Architect

Session Mission

Build a real-time, deterministic character-level tokenizer that converts raw text into sequences of Token IDs, manages vocabulary boundaries, and prepares data as torch.long tensors.

1. The Gateway to Logic

Raw Text is messy. A computer sees the word "Apple" as just a picture of pixels on a screen. For our local model to process language, we must transform it into a language the machine speaks: Numerical Sequences.

In Session 1, you built the containers (Tensors). Today, you engineer the infrastructure that fills them with data. Without this pipeline, your tensors are just empty lockers.

Important Reality Check

The model does not understand language semantically like humans do. It does not "know" what a cat is. Instead, it processes numerical relationships between token positions. It sees IDs, calculates probabilities, and predicts the next number.

The "Barcode" Analogy

Imagine a warehouse where the computer scanner can't read the word "Apple." It only knows Item #42. Tokenization is the process of assigning a unique, unchangeable ID to every character so the math can begin.

2. Vocabulary Discovery

Imagine trying to teach a robot how to read for the very first time.

The robot has never seen:

  • Letters
  • Words
  • Grammar
  • Meaning

To the machine, every character is just a symbol. Before our AI can process language, we must first define the complete list of symbols it is allowed to recognize.

This list becomes the model’s Vocabulary.

If a symbol does not exist inside this vocabulary, the AI has no mathematical way to represent it inside a tensor.

This is why vocabulary discovery is the first real preprocessing step in every language model pipeline.

3. Deterministic Mapping (stoi / itos)

Once we discover our vocabulary, we must assign every character a permanent numerical identity.

This process is called Deterministic Mapping.

Deterministic means:
→ the same character must always map to the same Token ID.

For example:


"A" → 5
"B" → 6
" " → 2

Imagine changing locker numbers in a school every morning. Students would never know where their books belong.

Language models work the same way. During training, the AI slowly learns relationships between Token IDs.
If those IDs suddenly change, all learned relationships become corrupted.

Stable Token IDs are what allow the model’s learned weights to remain meaningful across time.

🛠 Activity 2: Building Deterministic Token Mappings

Now that we know the vocabulary, we must assign every character a permanent numerical identity.

This creates the core translation infrastructure of the tokenizer.

We will build:

  • stoi → String To Integer
  • itos → Integer To String

These two dictionaries become the machine's language conversion system.

  1. Continue working inside your existing tokenizer_pipeline.py file.
  2. Copy the mapping code below underneath your vocabulary code.
    3. Building the Token Maps
    # stoi: string-to-integer (The Encoder)
stoi = { ch:i for i,ch in enumerate(chars) }

# itos: integer-to-string (The Decoder)
itos = { i:ch for i,ch in enumerate(chars) }

print("Character → Token ID Mapping:", stoi)

print(f"Mapping for 's': {stoi['s']}")

sample_id = stoi['s']
print(f"ID {sample_id} belongs to: {itos[sample_id]}")

Permanent Numerical Identity

Once these mappings are created, they become part of the model's language infrastructure.

During training, the AI learns relationships between these exact numerical IDs.

Example:

"s" → 18
"y" → 24
" " → 0

The model never sees the actual character.

It only learns patterns between token positions and token IDs.

Crossing Between Two Worlds

The encode() function is the gateway from the human world into the machine world.

It converts readable language into structured numerical sequences that the model can process mathematically.

encode() translates human-readable language into machine-readable numerical structure.

decode() performs the reverse operation:
it converts numerical sequences back into readable language.

Without these two functions, humans and language models would have no way to communicate with each other.

🛠 Activity 3: Engineering the Translation Pipeline

We now build the two most important functions in today's session:

  • encode() → converts language into Token IDs
  • decode() → converts Token IDs back into language

These functions form the gateway between:
→ human-readable language
→ and machine-readable numerical sequences.

  1. Continue working inside the same tokenizer_pipeline.py file.
  2. Copy the translation pipeline code below into your script.
    3. Building the Translation Pipeline
    # Text -> list of IDs
def encode(s):
    return [stoi[c] for c in s]
# list of IDs -> Text
def decode(l):
    return ''.join([itos[i] for i in l])

# Test the engineering
test_msg = "system"
encoded_seq = encode(test_msg)

print(f"Raw Input: {test_msg}")
print(f"Numerical Sequence: {encoded_seq}")
print(f"Decoded Output: {decode(encoded_seq)}")
  3. Run the file again using: 
    python tokenizer_pipeline.py
  4. Observe how the encode() function converts language into Token IDs.
  5. Verify that the decode() function reconstructs the original message correctly.
  6. Notice how human-readable text has now become machine-readable data.

5. Filling the Containers (Tensor Representation)

Until now, our encoded sequence has only existed as a normal Python list. But real AI models do not process ordinary Python lists.

They process Tensors.

This is where Session 1 connects directly into today's architecture.

Last session, you built the containers.
Today, you finally fill those containers with structured language data.

We use:
dtype=torch.long

because Token IDs behave like exact positions or indices inside the model.

Think of it like locker numbers in a school:

  • Locker #12 is valid
  • Locker #12.7 is meaningless

The model needs exact integer positions so it knows which learned representation to access. Once converted into a tensor, our text officially becomes machine-processable input.

Why Sequence Order Matters

Language models do not just care about which tokens exist.

They also care about the order of those tokens.

Example:

"DOG BITES MAN"
"MAN BITES DOG"

Both sentences contain the same words, but the sequence order completely changes the meaning.

This is why token positions become critically important inside transformer systems.

In future sessions, we will build mechanisms that help the model understand these positional relationships.

Why Not Just Use Python Lists?

Python lists are useful for general programming, but AI systems require optimized mathematical structures.

Tensors are designed for:

  • Fast numerical computation
  • Large-scale matrix operations
  • Parallel processing
  • GPU acceleration

In modern transformer systems, almost every operation eventually becomes tensor math.

Today, your language data officially entered that mathematical pipeline.

Understanding the Shape

If you see:


torch.Size([47])

this means:

  • The tensor has 1 dimension
  • It contains 47 token positions
  • Each position stores one Token ID

The AI does not see a sentence.

It sees a structured numerical sequence flowing through the architecture.

Engineering Insight: Why Token Efficiency Matters

Character-level tokenization creates very long sequences because every individual letter becomes its own token.

Example:


"H E L L O"
→ 5 separate tokens

Longer sequences require:

  • More memory
  • More computation
  • More attention calculations

This becomes expensive as models scale.

Modern LLMs solve this using advanced tokenizers like:

  • Byte Pair Encoding (BPE)
  • SentencePiece
  • TikToken

These systems combine common letter patterns into larger chunks so the model can process language more efficiently.

Our character-level tokenizer is intentionally simpler because it lets us clearly understand the architecture before introducing optimization complexity.

6. Controlled Failure: Vocabulary Boundaries

Breaking the System

What happens if you try to encode a character that wasn't in your original text (like an emoji 🚀 or a `~`)? Try it now in your code.

The Result: KeyError. This is a real-world engineering constraint. An LLM is physically unable to process or "see" anything that isn't inside its defined vocabulary.

Triggering a Vocabulary Failure
# Trigger a tokenizer failure
print(encode("🚀"))

What Just Happened?

The rocket emoji does not exist inside our vocabulary.

Since the tokenizer has no numerical identity assigned to this symbol, the system cannot encode it.

This causes a:

KeyError

Professional AI engineers intentionally trigger failures like this to test system boundaries and improve robustness.

⚙ Troubleshooting & FAQs

❓ KeyError: 'X'

The character 'X' isn't in your vocabulary. The system can only encode characters found in the original training text.

❓ torch.long vs torch.float

Token IDs represent exact positions inside the model's internal lookup system.

Think of it like opening lockers in a school:

  • Locker #12 exists
  • Locker #12.5 does not exist

The model uses Token IDs as exact integer indices to locate learned representations.

This is why token sequences must use:
torch.long

If you accidentally use floating-point numbers, later embedding layers will fail because they cannot index fractional positions.

❓ Case Sensitivity ( 'A' vs 'a' )

Python sees 'A' and 'a' as different characters. If your text only has lowercase letters, typing an uppercase letter will crash the tokenizer.

❓ Empty Vocabulary

If your set(text) results in 0 characters, your mappings will be empty and your functions will fail. Always ensure your source text is loaded correctly.

❓ Decode Mismatch

If decode(encode("hi")) doesn't return "hi", your stoi and itos maps are not aligned. Ensure they are both built from the same chars list.

Standard Task – Solution

Adding more symbols increases the vocabulary size because the tokenizer must assign a new Token ID to every unique character.

Example:

text = "HELLO!!! 🚀"

This introduces:

  • Uppercase letters
  • Punctuation
  • Emoji characters

Converting everything into lowercase using:

text.lower()

usually reduces the vocabulary size because:


"H" and "h"

become the same character.

Smaller vocabularies are easier to manage and require fewer unique Token IDs.

However, token efficiency also depends on sequence length.

Modern LLMs balance both:
→ vocabulary size
→ and sequence efficiency.

Advanced Task – Solution

Safer Encoding Logic
def encode(s):
    output = []

    for c in s:
        if c in stoi:
            output.append(stoi[c])
        else:
            print(f"Warning: '{c}' not in vocabulary. Skipping.")

    return output

Important Tradeoff:

Skipping unknown characters prevents the system from crashing, but it also removes information from the original input.

Example:

"Hello 🚀"

may become:

"Hello "

after encoding and decoding.

Real-world AI systems solve this using:

  • Special unknown tokens like <UNK>
  • Larger vocabularies
  • More advanced tokenization systems

Explanation:

Instead of crashing with a KeyError, the tokenizer now safely handles unsupported characters.

Real-world AI systems require:

  • Graceful error handling
  • Input validation
  • Robust preprocessing pipelines

This is one of the first steps toward building production-grade AI infrastructure.

Did You Know?

GPT-4 doesn't tokenize letters; it uses "Byte Pair Encoding" (BPE). It groups common patterns like "the" or "ing" into a single ID. This is why it can "read" much faster and fit more information into its context window than our character-level model!
