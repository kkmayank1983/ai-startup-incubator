1. Why It Cannot Answer

A model can only copy the patterns in its book

Your model has read one thing its whole life: a Shakespeare play. So it learned the patterns in a play — which character speaks next, how a line of verse tends to run.

A play has no questions and answers in it. Nobody asks "what is gravity?" and gets a reply. So the model has never once seen the pattern "a question was asked → now give an answer → now stop". It cannot copy a pattern it has never seen.

Today's whole idea, in one line

If you want different behaviour, change the book — not the brain. Your engine is fine. It has simply been reading the wrong thing.

4. The Upgrade: Whole Words Instead of Letters

Before we start: this is a stepping stone

What you are about to build is not the tokenizer we finish with. Whole words fix the spelling problem, and then break something else — you will find the break yourself at the end of today.

We are building it anyway, on purpose. Characters showed you one extreme, words show you the other, and next session you build the one real AI models actually use, which sits in the middle. You cannot appreciate why that one is clever until you have felt both of these fail.

What if a token was a whole word?

Then the model picks gravity in one go, from a list:

gravity

It becomes impossible to misspell. Not unlikely — impossible. Every word it writes comes from a list of real words, so a broken word cannot come out.

And the change is one word of code

Session 2 collected every unique character. We now collect every unique word. It is the same idea, pointed at something bigger:

Session 2 — characters
chars = sorted(list(set(text)))
Session 6 — words
words = sorted(list(set(text.split())))

.split() cuts text wherever there is a space. That is the entire upgrade.

data_pipeline.py — replace the tokenizer section
# --- The tokenizer, now split on WORDS instead of characters ---
# Session 2 did:  chars = sorted(list(set(text)))
# One added .split() and every token is now a whole word.
words = sorted(list(set(text.split())))
stoi = { w:i for i,w in enumerate(words) }
itos = { i:w for i,w in enumerate(words) }

vocab_size = len(words)      # how many different WORDS exist

# Unknown words are dropped, because the model has no number for them.
def encode(s):
    return [stoi[w] for w in s.split() if w in stoi]

def decode(ids):
    return ' '.join([itos[i] for i in ids])

🛠 Activity 3: Train On The New Book

  2. Copy in the code below.
  3. Run it. It takes about 5 minutes — watch the loss fall while you wait.
train_qa.py
import torch
import torch.nn.functional as F

# Same seed as Session 5, so a re-run gives the same model.
torch.manual_seed(1337)

from data_pipeline import data, vocab_size, decode, encode
from attention_engine import model, block_size, batch_size

STEPS = 1500

print(f"Vocabulary   : {vocab_size} words")
print(f"Dataset      : {len(data)} tokens")
print(f"Model params : {sum(p.numel() for p in model.parameters()):,}")

optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)

print("\nTraining on the question-and-answer data...")
running = 0.0
for step in range(1, STEPS + 1):
    ix = torch.randint(0, len(data) - block_size - 1, (batch_size,))
    x = torch.stack([data[i:i + block_size] for i in ix])
    y = torch.stack([data[i + 1:i + block_size + 1] for i in ix])

    logits = model(x)
    loss = F.cross_entropy(logits.view(-1, vocab_size), y.view(-1))

    optimizer.zero_grad()
    loss.backward()
    optimizer.step()

    running += loss.item()
    if step % 300 == 0:
        print(f"  step {step:5d} | average loss {running/300:.3f}")
        running = 0.0

# --- Save it, so you never have to train again ---
torch.save(model.state_dict(), "qa_model.pth")
print("\nSaved qa_model.pth")

# --- Ask it something straight away ---
prompt = "<|user|> What is gravity? <|assistant|>"
ids = torch.tensor([encode(prompt)], dtype=torch.long)
answer = model.generate(ids, max_new_tokens=60)[0].tolist()

print("\n" + "=" * 55)
print("YOUR MODEL, ANSWERING A QUESTION")
print("=" * 55)
print(decode(answer[len(encode(prompt)):]))

How train_qa.py works, part by part

1
torch.manual_seed(1337)

Fixes every "random" choice — the starting weights, and which chunks of the book each step grabs. Run it twice and you get the identical model.

Why it is the very first line: it must run before the model is built, or the starting weights are already random by the time you fix the seed. Same trick as Session 5.
2
from data_pipeline import ... / from attention_engine import ...

Everything comes from files you already have. data_pipeline gives the book as numbers and the word list; attention_engine gives the model itself.

Importing a file runs it — which is why you see data_pipeline's own printout appear first. Not a bug.
3
STEPS = 1500

How many times the model practises. Section 6 explains why this is 1,500 and not Session 5's 6,000 — the short version is that this book is 50 times smaller.

4
optimizer = torch.optim.AdamW(...)

The part that actually adjusts the model. Once we know which way each number should move, AdamW moves it a little. lr=1e-3 is how big that step is.

Same optimizer you used in Sessions 4 and 5. Nothing new here.
5
ix = torch.randint(...) — grabbing a batch

Picks 64 random starting points in the book. From each it takes 64 tokens as the input x, and the same 64 shifted one place along as the answer y.

That one-place shift is the whole task: at every position, the right answer is simply the next word.

Nobody labelled this data. The book labels itself — which is why models can learn from plain text.
6
logits = model(x) — the guess

All 64 chunks go through the model at once. Out comes a score for every one of the 4,095 words, at every position.

7
loss = F.cross_entropy(...) — the marking

Compares each guess against the word that actually came next, and turns the whole lot into a single number: how surprised were you?

8
zero_grad() → backward() → step()

Three lines, always in this order. Wipe last step's notes, work out which way every number should move, then move them.

Forget zero_grad() and PyTorch adds the new notes onto the old ones. The model still trains, just wrongly, and slowly gets worse in a way that looks like a bad learning rate. The most common bug in hand-written training loops.
9
if step % 300 == 0: print(...)

Every 300 steps, print the average loss since last time. Averaging matters — a single step bounces around too much to tell you anything.

10
torch.save(model.state_dict(), "qa_model.pth")

Writes every learned number to a file. state_dict is PyTorch's name for that bundle.

This is the line that ends the retrain-every-time misery. It is also, in miniature, exactly how every AI you have used is shipped: train once, save, load forever.
11
The question at the end

Builds the prompt <|user|> What is gravity? <|assistant|>, feeds it in, and prints what comes out — so you find out whether the run worked without opening another file.

The important new line

torch.save(model.state_dict(), "qa_model.pth")

Until now, every time you wanted to chat, your model retrained from scratch. This line writes everything it learned into a file. Train once, use forever. That file is your model — and it is the first one you will actually keep.

6. Why 1,500 Steps? Understanding the Dials

🔍 Session 5 trained for 6,000 steps. Why did we drop to 1,500?

It looks like we are being lazy. We are not. Look at what a "step" actually costs on each book.

Every step, your model reads 64 chunks of 64 tokens — that is 4,096 tokens per step. So the real question is: how many times does it read the whole book?

The number that decides everything

Session 5 Session 6
Book size 1,115,394 tokens 22,182 tokens
Steps 6,000 1,500
Times it reads the whole book 22 277

Your new book is 50 times smaller. So even at a quarter of the steps, your model reads it 277 times — against Shakespeare's 22.

And if we had kept 6,000 steps? It would read these same 399 questions 1,108 times over. Nobody learns anything new on the thousandth read. They just learn it by heart.

What "loss" actually measures

Loss is how surprised the model was by the right answer. Nothing more.

At every position it guesses the next token. Then we look at what actually came next and ask: how much did you expect that?

  • Expected it strongly → loss near 0
  • Total shock → loss large

Your run went 5.182 → 0.690. It started off astonished by every word, and ended up mostly expecting what came next. That is real learning — the model found patterns.

The trap: a lower loss does NOT mean better writing

This is the single most useful thing in today's session, so here is real proof from your own model.

We tried making the model bigger — a whole extra round of look-and-think. One change, nothing else touched:

Loss Sensible word pairs Copied word-for-word
Your model 0.594 87.1% 3.7%
Bigger model 0.401 — much better! 88.2% — no real change 6.0% — nearly doubled

The loss fell by a third. The writing did not improve. What improved was its memory of the answer sheet. That is why we do not simply chase a smaller number.

🔍 So what is really happening as the steps go up?

  1. Early on the model learns real patterns — that <|assistant|> follows a question, that "force" often follows "the".
  2. Later it runs out of new patterns to find. There are only 399 questions.
  3. So it starts memorising whole phrases. Loss keeps dropping, because reciting is a very reliable way to be unsurprised.

We measured exactly this. At 750 steps 0% of its writing was copied word-for-word from the book. At 1,500 steps it was creeping up. Push on to 6,000 and you get a model that recites your book back at you — with a beautiful loss number and nothing learned.

Every dial in your files, and what it does

Setting Yours What it does — and why it is set there
STEPS 1,500 How many times it practises. Too few and it hasn't found the patterns. Too many and it memorises. 1,500 is where it writes well without reciting.
block_size 64 How much it sees at once. We did not raise it — because 64 words is already a whole question plus most of an answer. It used to be 64 letters. The tokenizer did that job for us.
batch_size 64 How many chunks it studies together before adjusting itself. Bigger means steadier — one odd chunk can't yank the whole model sideways.
n_embd 96 How many numbers describe one token. Think of it as how much the model is allowed to remember about a word — is it a noun? about force? plural?
nn.Embedding 4,095 × 96 The lookup table. One row of 96 numbers per word. Feed in word 2,568 and out comes row 2,568 — the numbers that mean "gravity" to your model.
nn.Linear several Where the learning actually lives. Each one multiplies its input by a grid of numbers that training adjusts. Your Query, Key, Value and the thinking step are all these.
vocab_size 4,095 How many options it chooses between at every single position. It went from 86 to 4,095 today — a much harder choice, but every option is now a real word.

Add all those numbers up and you get your model's size: 842,751 parameters. Most of them live in that embedding table and the final layer, because both have to cope with 4,095 different words.

The lesson hiding in all of this

Today you changed two things and left the model alone:

Change Effect on the writing
Swapped the tokenizer 12.5% → 87% sensible word pairs
Made the model bigger 87.1% → 88.2% — almost nothing

When your dataset is small, how you feed the model matters far more than how clever the model is. That is why today was about data and tokens, not about the engine. Bigger engines start earning their keep in Term 3 — once there is enough data to feed them.

7. Talk To It

Set your expectations first — this is important

You are about to type a question and get a reply. It will not actually answer you. Do not expect a tutor.

What you built is an autocomplete engine. It has one skill: look at the text so far, guess the next word. That is all it has ever done. When you type "What is gravity?" it does not understand a question has been asked — it just continues the text in the style it has read.

Sometimes that continuation looks like an answer. Sometimes it carries on writing another question. Both are the same behaviour.

Today's goal was never "answer correctly". It was "produce real English words", and you have done that.

Why it cannot answer properly yet — three honest reasons

Yours today The model in Term 3
Size (parameters) 842,751 12,219,525 — 14x bigger
Reading material 22,182 tokens 7,505,033 — 338x more
Practice 1,500 steps 10,000 steps

399 questions is simply not enough material to learn what physics means. It is enough to learn what physics writing sounds like — and that is precisely what you are seeing.

🔍 Two changes to a file you already have

Open your talk_to_your_engine.py from Session 5. Two things are different now:

  1. It loads the saved model instead of importing the training script. No more waiting.
  2. It wraps your question in signposts before sending it — <|user|> your question <|assistant|> — so the model sees the exact shape it was trained on.

Why you never see the signposts in the reply

The model absolutely does write <|user|> and <|assistant|> into its output — it learned them from the book, so it uses them. Two lines of code hide them, and it is worth knowing exactly how.

Step 1 — throw away the prompt.

answer = decode(result[len(ids):])

generate() hands back your question and the new text joined together. Your question already contained two signposts, because you wrapped it in them. Slicing from len(ids) keeps only what the model actually added.

Step 2 — stop at the first signpost.

for tag in ("<|endoftext|>", "<|user|>", "<|assistant|>"):
    answer = answer.split(tag)[0]

The model does not stop when it finishes an answer. It carries straight on and starts inventing a whole new conversation. split(tag)[0] keeps only the part before the first signpost — so you see one answer instead of an endless stream. We check all three tags, because whichever one it writes first is where the answer really ended.

🛠 Activity 4: Ask Your AI A Physics Question

  1. Open talk_to_your_engine.py and replace everything in it with the code below.
  2. Run it and ask a question.
talk_to_your_engine.py
import torch

# No training this time. The model is loaded from the file you saved.
from attention_engine import model, block_size
from data_pipeline import stoi, encode, decode

model.load_state_dict(torch.load("qa_model.pth"))
model.eval()

print("\n" + "=" * 55)
print("ASK YOUR AI A PHYSICS QUESTION")
print("=" * 55)
print("Type a question. Type  quit  to stop.\n")

while True:
    question = input("You: ")
    if question.lower() == "quit":
        break

    missing = [w for w in question.split() if w not in stoi]
    if missing:
        print(f"   (these words are not in the vocabulary, so they were dropped: {missing})")

    # Wrap the question the same way every block in input.txt is wrapped.
    prompt = f"<|user|> {question} <|assistant|>"
    ids = encode(prompt)
    if not ids:
        print("   (nothing left for the AI to read)\n")
        continue

    context = torch.tensor([ids[-block_size:]], dtype=torch.long)
    result = model.generate(context, max_new_tokens=60)[0].tolist()

    # Step 1: drop the prompt. generate() returns your question AND the new
    # text, so we keep only the part after what we fed in.
    answer = decode(result[len(ids):])

    # Step 2: stop at the first signpost. The model keeps writing after it
    # finishes an answer -- it starts a whole new question. Cut it off there.
    for tag in ("<|endoftext|>", "<|user|>", "<|assistant|>"):
        answer = answer.split(tag)[0]

    print("\nAI: " + answer.strip() + "\n")

Punctuation is the sneakiest — because we split on spaces, gravity? and gravity are stored as two separate entries, which is part of why the vocabulary reached 4,095.

Advanced Task — what to expect

At 3,000 steps the answers get smoother, and something else creeps in: whole phrases start coming back word for word from the training file. We measured it — at 1,500 steps about 3.7% of what it writes is copied verbatim, and that climbs with more training.

That is memorising, not understanding. With only 399 questions there simply is not enough material to learn general patterns, so the model starts reciting. It is the honest reason we stopped at 1,500.

Engineering Takeaway

More training is not automatically better. Past a point, a model stops learning the subject and starts learning the answer sheet. The only way to spot it is to check whether the output is copied — the loss number looks wonderful either way.

Did You Know?

The very first version of Google Translate's neural model used whole words, exactly like yours — and hit exactly the same wall. Their vocabulary reached 80,000 words and it still could not handle names, typos or new words. That problem is what led directly to the technique you will build next session.

Next Mission: Smarter Tokens

Characters can spell anything but write nonsense. Words write beautifully but only know 4,095 things. Next session you build the tokenizer that gets both — it splits words into common chunks, so Explain and photosynthesis both work, and it is the exact method behind every AI you have heard of.

⚙ Troubleshooting & FAQs
❓ KeyError when I run data_pipeline.py

You changed chars to words in some places but not others. Every one of stoi, itos and vocab_size must be built from words, not chars.

❓ FileNotFoundError: qa_model.pth

You have not run train_qa.py yet, or it stopped before finishing. The chat script loads that file — it cannot run until training has saved it once.

❓ My model prints data_pipeline's output too

Normal — importing a file runs it, exactly as in Session 4. Comment out the print() lines at the bottom of data_pipeline.py if you want a cleaner screen. Only the prints.

❓ RuntimeError about size mismatch when loading qa_model.pth

You saved the model with one vocabulary and are loading it with another — usually because input.txt changed after training. Re-run train_qa.py to rebuild the file.

❓ The answers wander off topic

Expected, and honest. With 399 questions and a small engine, the model has learned what physics writing sounds like far better than what any particular question means. Term 3 fixes this with a far bigger dataset.

❓ Training is taking much longer than 5 minutes

Check STEPS = 1500 at the top of train_qa.py. If you also have other programs running, close them — this is doing real arithmetic on your processor.
