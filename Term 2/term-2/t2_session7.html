2. Build Four Heads

Each head reads the same token with n_embd = 96 inputs, but produces a smaller 24-number report. Four reports restore the 96-number output the engine expects:

The one rule

n_head must divide n_embd evenly. Four works because 96 ÷ 4 = 24. Five fails because 96 ÷ 5 = 19.2.

class MultiHeadAttention(nn.Module):
    """Several Attention Heads running side by side.

    Each head gets a SMALLER slice of the numbers to work with, and
    goes hunting for its own kind of relationship. We stick their
    answers back together at the end."""
    def __init__(self, num_heads, head_size):
        super().__init__()

        # Build num_heads copies of the head you already wrote.
        self.heads = nn.ModuleList(
            [SelfAttentionHead(head_size) for _ in range(num_heads)]
        )

        # Sticking together is not the same as mixing together.
        # This layer lets what the heads found blend into each other.
        self.proj = nn.Linear(n_embd, n_embd)

    def forward(self, x):
        # Each head hands back head_size numbers per token.
        # 4 heads x 24 numbers = the 96 we started with.
        out = torch.cat([h(x) for h in self.heads], dim=-1)

        return self.proj(out)
Wasself.sa_head = SelfAttentionHead(n_embd)
Nowself.sa_head = MultiHeadAttention(n_head, n_embd // n_head)

// means whole-number division, so 96 // 4 is 24.

3. Add LayerNorm

First: what is a residual connection?

At this point, x holds 96 numbers for every token. Those numbers already contain what the engine knows about the word and its position.

Attention should add useful context to that information—not throw the original away. The engine therefore sends x along two paths:

  1. Shortcut path: keep the original x unchanged.
  2. Working path: send a copy through LayerNorm and attention to calculate new information.

The two paths meet at the + sign. This shortcut from a layer’s input to its output is the residual connection. The layer only has to learn the remaining change—the “residual”—that should be added.

Think of a worksheet and a sticky note: the original worksheet travels along the shortcut unchanged. Attention writes a useful hint on the sticky note. The + attaches the hint to the original instead of replacing the worksheet.

Why keep the shortcut?

The layer learns only a useful correction, not how to rebuild everything. If an update is unhelpful, the earlier information is still available.

Why two residuals?

Attention adds a context update. Feed-forward adds a thinking update. Each update gets its own shortcut and +.

Why LayerNorm?

Repeated additions can make some features huge and others tiny. LayerNorm steadies the working copy before each update.

Now the LayerNorm problem makes sense: every block adds two updates. Stack many blocks and those numbers can drift onto very different scales. LayerNorm puts one token’s 96 features back on a workable scale before attention or feed-forward uses them.

Activity 2: Add LayerNorm (3 lines)

Inside PredictionEngine.__init__, add:

self.ln1 = nn.LayerNorm(n_embd)   # tidy up before attention
self.ln2 = nn.LayerNorm(n_embd)   # tidy up before thinking

Then update these two lines in forward:

attention_engine.py — inside forward()
        x = x + self.sa_head(self.ln1(x))   # focus, then add the result back in
        x = x + self.ffwd(self.ln2(x))      # think about it, then add that back in too

Read the first line from the inside out: ln1 steadies a copy of x → the attention heads calculate an update → + adds that update to the untouched shortcut → x = stores the combined result.

The second line repeats the same pattern for feed-forward. Normalising before each working layer is called pre-norm.

see_the_heads.py
import torch

from data_pipeline import encode, itos
from attention_engine import model, n_head

# Load the model you just trained.
model.load_state_dict(torch.load("qa_model_v2.pth"))
model.eval()

SENTENCE = "The magnet pulls the iron because it is magnetic"

ids = encode(SENTENCE)
words = [itos[i] for i in ids]

# Running the model fills in .last_weights inside every head.
with torch.no_grad():
    model(torch.tensor([ids]))

print("Sentence:", " ".join(words))
print()
print("Each column is one head. For every word, we show the word it")
print("paid the MOST attention to.")
print()

header = f"{'word':<12}" + "".join(f"head {h+1:<8}" for h in range(n_head))
print(header)
print("-" * len(header))

for pos, word in enumerate(words):
    row = f"{word:<12}"
    for h in range(n_head):
        wei = model.sa_head.heads[h].last_weights[0]   # (T, T)
        best = torch.argmax(wei[pos]).item()           # who did it look at?
        row += f"{words[best]:<13}"
    print(row)

print()
print("If every column were identical, the extra heads would be pointless.")

6. Race the Two Engines

Activity 5: Create showdown.py

This loads both saved models and gives them the same questions and random seeds.

Show the complete script
showdown.py
import torch

from data_pipeline import encode, decode

# engine_v1.py is the copy you made BEFORE editing -- one head, no LayerNorm.
from engine_v1 import model as model_v1
from attention_engine import model as model_v2

model_v1.load_state_dict(torch.load("qa_model.pth"))
model_v2.load_state_dict(torch.load("qa_model_v2.pth"))
model_v1.eval()
model_v2.eval()

QUESTIONS = [
    "Why do kitchen fridge doors snap shut tightly on their own when you get them close?",
    "Why do garbage recycling centers use giant magnets above their conveyor belts?",
    "Does friction depend on surface area?",
]


def ask(model, question, seed):
    torch.manual_seed(seed)          # same seed for both, so it is a fair race
    prompt = f"<|user|> {question} <|assistant|>"
    ids = encode(prompt)
    out = model.generate(torch.tensor([ids]), max_new_tokens=45)[0].tolist()
    answer = decode(out[len(ids):])
    for tag in ("<|endoftext|>", "<|user|>", "<|assistant|>"):
        answer = answer.split(tag)[0]
    return answer.strip()


p1 = sum(p.numel() for p in model_v1.parameters())
p2 = sum(p.numel() for p in model_v2.parameters())

print("=" * 60)
print("SHOWDOWN: Session 6 engine  vs  Session 7 engine")
print("=" * 60)
print(f"v1  1 head,  no LayerNorm : {p1:,} parameters")
print(f"v2  4 heads, LayerNorm    : {p2:,} parameters")
print(f"difference                : {p2 - p1:,} more  ({(p2-p1)/p1*100:.1f}%)")

for n, q in enumerate(QUESTIONS):
    print("\n" + "-" * 60)
    print(f"Q: {q}")
    print("-" * 60)
    print(f"v1: {ask(model_v1, q, 100 + n)}")
    print()
    print(f"v2: {ask(model_v2, q, 100 + n)}")

Bonus concept: why position embeddings matter

Attention compares words but does not automatically know their order. These sentences contain the same words but mean opposite things:

the dog bit the man
01234
the man bit the dog
01234
tok_emb = self.token_embedding_table(idx)                # what word is this?
pos_emb = self.position_embedding_table(torch.arange(T)) # where does it sit?
x = tok_emb + pos_emb                                    # combine both cards

There is nothing new to type: this code is already in your engine. The token card says what; the position card says where.

Bonus engineering lesson: famous techniques still need testing

Top-k lets generation choose only from the k most likely next words. On this small, over-confident model, top-k 40 and top-k 100 produced identical measured results—the discarded words already had almost no chance.

Temperature did change the output. Lowering it to 0.6 made word pairs more sensible (92.7%) but increased copying (8.3%). Cleaner text came with more memorisation.

Takeaway: a technique can be useful in general and useless for your current problem. Measure before you keep it.

Need Help? View Expected Results

Head count: more heads is not automatically better. Two heads get 48 dimensions each; four get 24; eight get 12. Very thin heads may lack room to learn useful patterns.

No position: our four-head test worsened from 0.443 to 0.541 loss, even though some generated text looked smooth. Without order information, the model can produce vague but plausible-sounding phrases.
