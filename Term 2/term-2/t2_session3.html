Session 3: The First Prediction Engine

Language models don't "think"—they predict. Today, you build the first logic layer of your machine: the engine that calculates what comes next.

60 Minutes Level: Junior Architect

Session Mission

1. From Static Data to Dynamic Generation

In Session 2, we built the gateway (The Tokenizer) to turn words into numbers. But a list of numbers is just static data. To create an AI, we need a Prediction Engine.

The core mechanic is Autoregression: the system looks at its current position, predicts one single token, and then feeds that token back into itself to predict the next. It is a continuous loop of "What is the most likely next number?"

2. The "Score Table" Intuition

Before writing code, we need a way for the machine to store its "opinions" on which characters follow each other. We need a Score Table.

Imagine a grid where every character the AI knows has its own Row, and every possible next character has its own Column:

Current Token ↓ Next: "u" Next: "a" Next: "z"
"q" 9.5 (High) 0.2 -2.1

PyTorch provides a tool called nn.Embedding which is simply a convenient way to store and search this giant table of scores. It doesn't create intelligence; it just holds the scores that represent the model's prediction tendencies.

🛠 Activity 1: Building the Score Table Infrastructure

We are now building the first prediction component of our language model.

The tokenizer from Session 2 can already convert language into Token IDs.

Our next challenge is teaching the machine how to make predictions from those IDs.

To do this, we need a structure that stores prediction scores for every possible token.

We will use nn.Embedding as the storage system for our Score Table.

    import torch
import torch.nn as nn
from torch.nn import functional as F

class PredictionEngine(nn.Module):
    def __init__(self, vocab_size):
        super().__init__()

        # Store prediction scores for every token
        self.score_table = nn.Embedding(vocab_size, vocab_size)

    def forward(self, idx):
        logits = self.score_table(idx)
        return logits

model = PredictionEngine(65)

3. From Raw Opinions to Choices: The Weighted Dice

Logits (raw scores) are hard for us to use because they aren't standardized. To make a choice, we follow a 3-step pipeline:

  1. Raw Scores (Logits): Random numbers like 10.5, -2.1, 0.4.
  2. Probabilities (Softmax): We "squash" these numbers so they all become positive and add up to exactly 100%.
  3. Sampling: We treat these percentages as a Weighted Die. A character with a 90% probability takes up 90% of the die's surface.

We roll the die to pick the next token. This introduces controlled randomness into generation. Instead of always choosing the single highest-scoring token, the model can occasionally explore other plausible options. Once the model has learned real language patterns, this helps generation feel more natural and less repetitive.

🛠 Activity 3: Engineering the Feedback Loop

The model can now produce prediction scores.

Next, we must teach it how to generate language.

This requires a continuous feedback loop:

Current Token
↓
Prediction
↓
New Token
↓
Feed Back Into System
↓
Repeat

This process is called Autoregression.

  1. Continue working inside generation_engine.py.
  2. Add the generate() function inside the PredictionEngine class.
  3. Copy the code below exactly.
    4. Add inside PredictionEngine
    def generate(self, idx, max_new_tokens):
    for _ in range(max_new_tokens):

        logits = self(idx)

        logits = logits[:, -1, :]

        probs = F.softmax(logits, dim=-1)

        idx_next = torch.multinomial(probs, num_samples=1)

        idx = torch.cat((idx, idx_next), dim=1)

    return idx

Understanding the Feedback Loop

Let's imagine our current sequence contains a single token: 

[5]

The model looks at this token and predicts the next token: 

42

We store this prediction in: 

idx_next = [[42]]

Then this line runs: 

idx = torch.cat((idx, idx_next), dim=1)

The sequence now becomes: 

[5, 42]

On the next loop iteration, the model no longer sees only [5]. It now sees: 

[5, 42]

The newly generated token has been added back into the sequence. This is the Feedback Loop that allows the model to generate text one token at a time.

5. Controlled Failure: The Context Problem

Why doesn't it make sense?

Look at your output. Can the model even finish the word "The"?

The Discovery: No. Because this model only looks at the current token to guess the next, it has "Zero Memory." If the model sees the letter "h", it has no idea if the previous letter was "T" or "s".

Engineering Lesson: One-token memory is not enough to model language effectively. The machine needs access to a larger history of previous tokens before it can make meaningful predictions.

This creates the architectural necessity for a Context Window, which we will build in Session 4.

⚙ Troubleshooting & FAQs

❓ RuntimeError: index out of range

This usually means your vocab_size in the model (65) is smaller than the Token IDs being produced by your tokenizer. They must match exactly.

❓ What exactly are "Logits"?

Think of logits as the model's raw preferences.

Higher logits indicate stronger preference for a token. Lower logits indicate weaker preference.

These values are not probabilities yet. Softmax converts them into probabilities that can be used for sampling.

❓ Why are some logits negative?

Logits can be positive or negative.

A negative logit does not mean the token is impossible. It simply means the model currently prefers that token less than tokens with higher logits.

Softmax will still convert all logits into valid probabilities.

❓ Why do my logits change every time I run the program?

The Score Table is randomly initialized every time the model starts.

Since the logits come directly from this table, they will be different each time you restart the script.

Later in the curriculum, training will replace these random values with learned language patterns.

❓ What is "grad_fn=<EmbeddingBackward0>"?

This is information added by PyTorch.

It tells PyTorch how the tensor was created so that the model can learn during training.

You can safely ignore it for now. We will revisit this concept when we study training and optimization later.

❓ Why use softmax instead of just picking the highest score?

If we always pick the highest score, the AI will always make the same choices repeatedly.

Softmax combined with sampling introduces controlled randomness, allowing the model to explore multiple plausible predictions instead of always choosing the single highest-scoring option.

❓ Why didn't anything new appear after adding the generate() function?

Defining a function does not execute it.

In Activity 3, we only built the generation machinery. The function is not actually used until Activity 4 when we call: 

model.generate(...)

❓ What does "the model's output becomes its next input" mean?

The newly generated token is added back into the existing sequence.

For example: 


Current Sequence: [5]

Model Predicts: 42

Updated Sequence: [5, 42]

On the next loop iteration, the model uses the updated sequence as its new input. This creates the Feedback Loop that allows continuous text generation.

❓ Why am I seeing Token IDs instead of words?

Internally, language models work with numerical tokens rather than readable text.

We used the decoder from Session 2 to convert those Token IDs back into characters so that we could inspect the generated output.

❓ Why does the decoded output look like gibberish?

The generation architecture is working correctly.

The output looks random because the Score Table currently contains random values and the model has not learned any language patterns yet.

The model also has no memory of previous words or sentences, so it cannot maintain meaningful context.

Solving that memory problem is the goal of Session 4.

❓ Why do I get different generated text every time I run the script?

The Score Table is randomly initialized each time the model starts.

The generator also uses random sampling when selecting the next token.

Because of this, the generated output will usually be different every time you run the program.

Standard Task – Explanation

Real words appear purely by chance.

The generator is producing thousands of random character combinations.

When enough random combinations are created, some of them will accidentally form short real words such as "a", "to", or "is".

This does not mean the model understands language. It simply means that random generation occasionally produces recognizable patterns.

Advanced Task – Solution

# Force 'z' to become the preferred prediction after 'a'

with torch.no_grad():
    model.score_table.weight[0, 25] = 50.0

print("Modified Score Table Successfully")

In the example above, we are using the character list from Activity 4, where:

  • 0 represents 'a'
  • 25 represents 'z'

If your vocabulary uses a different character ordering, the corresponding IDs may be different.

Why This Matters

Earlier in this session, the model's scores were completely random.

By manually changing a single value in the Score Table, you changed the model's behavior.

Modern AI training works the same way—but instead of changing one score, the computer automatically adjusts millions or billions of scores until useful patterns emerge.

Engineering Insight: By doing this, you are performing "Manual Training." You changed a single score manually.

During real training, the computer automatically adjusts millions of scores like this by reading large amounts of text and measuring its mistakes.

Training is simply the process of improving the Score Table.

Did You Know?

When ChatGPT generates a long answer, it doesn't create the entire response at once. It predicts one token, then the next, then the next—repeating this process hundreds or even thousands of times before you see the final message.
