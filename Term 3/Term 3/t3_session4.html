Words you will meet today

The book — input.txt. Twenty subjects, written as conversations between a student and a tutor. It is the only thing the model ever learns from.
A block — one conversation in the book: a topic line, a student's question and a tutor's reply, with tags around them.
A chunk — 256 word pieces cut from the book at a random spot. One chunk is one "page" the model reads during training.
A tag — a special word piece like <|assistant|> that says "the tutor's reply starts here". Signposts, not words.
A mark — how wrong one guess was. The loss is the average of all the marks. Lower is better.
Graded — a word piece the red pen is allowed to mark. Today, only the tutor's reply is graded.
A step — the model reads 64 chunks, gets marked, and nudges its numbers once. Training is 14,000 steps.
A trip through the book — enough steps to have read every word piece in the book once. v6 made about six trips.

1. What Gets Marked

In one sentence Right now the model is marked on guessing the student's question as well as the tutor's reply. Today we stop marking the question, because the model never has to write one.

First, what one block of the book looks like

Every conversation in input.txt has the same shape. Here is one, with the four kinds of word piece coloured in. Keep this picture in mind for the whole session.

Think of training as a teacher with a red pen

Here is how training works. The model reads a chunk of the book, 256 word pieces long. At every spot it guesses what word piece comes next. Then a red pen marks every guess: a small mark if the guess was close, a big mark if it was far off. The loss is the average size of those marks. Every change to the model's 8 million numbers comes from that one average.

Here is the problem. The chunk is cut from the book at a random spot, so it has everything in it: the topic line, the tags, the student's question and the tutor's reply. And the red pen marks every single word piece the same way.

Two things to notice. The TOPIC line and the tags cost almost nothing. The model learned them early and never gets them wrong. But a quarter of all the marks land on the student's question. That is the hardest text in the book to guess (half of it is lowercase, casual, and has typos on purpose), and it is the one thing the model will never have to write.

What that table says, in plain words Picture 100 red marks. About 73 of them land on the tutor's replies, which is right. But about 25 land on the student's questions. Those 25 are wasted. The model is being told off for not guessing a stranger's typo, and it will never have to type one. The topic lines and tags barely count: the model learned those in the first few minutes and never gets them wrong.

The model's job is to answer, so mark the answer

When you chat with the model, you type the question. The model only ever writes the reply. Every bit of effort spent learning to guess "so digestion starts befre eating?" is effort not spent on what digestion actually is.

So from today the red pen skips the question. The model still reads it, because it has to know what was asked. It just is not marked on it any more.

Check yourself: after today's change, does the model still see the student's question while it trains?

Yes. The question is still in every chunk the model reads, and it has to understand it to write a good reply. The only difference is that the red pen no longer marks the model's guesses inside the question. Reading and being marked are two different things.

2. It Has Only Read Each Fact Six Times

In one sentence v6 stopped learning after it had read the book about six times, and it was still improving when it stopped. So v7 picks up exactly where v6 left off and reads the book six more times.

The second reason the facts are blurry

The book has about 38,400 facts across twenty subjects. Each fact shows up in about eleven or twelve blocks, so the whole book is 533,000 blocks and 44 million word pieces long.

Session 3's training read 229 million word pieces (14,000 steps × 64 chunks × 256 pieces). That sounds like a lot. It is only 5.6 trips through the book. So v6 has seen each fact about six times.

Imagine reading a textbook with 38,400 facts in it six times, then sitting the exam. You would remember some of it. The model's loss was still going down when Session 3's run stopped. It had not finished learning. It just ran out of time.

Change 2: do not start again from zero
Every session so far

Load qa_model_v6.pth. Train it 14,000 more steps with the new marking. Save it as v7. Twelve trips through the book instead of six, for the same two hours.

🔨 Activity 1: Mark where the answers are

What this activity builds A long list of True/False, one for every word piece in the whole book. True means "this piece is inside a tutor's reply, so the red pen may mark it". False means "skip it". The training loop will use this list in Activity 2.

The idea: a light switch

Walk through the book one word piece at a time, holding a light switch.

  • When you pass an <|assistant|> tag, switch the light on. A reply has started.
  • When you pass an <|endoftext|> tag, switch the light off, but only after that tag. The tag itself still counts, because the model has to learn to write it.
  • A word piece is graded if the light is on when you reach it.

The code below is exactly this light switch, written for the whole book at once.

Open train_qa.py. Find the line that imports from data_pipeline and add stoi to it. stoi is the dictionary that turns a word piece into its number, and you need the numbers of two tags:

train_qa.py — OLD, then NEW
from data_pipeline import data, vocab_size, decode, encode

from data_pipeline import data, vocab_size, stoi, encode, decode

Now, directly under the LEARNING_RATE line, add this block. It goes through the whole book once and makes a list of True/False, one for every word piece: True if that piece is inside a tutor's reply, False if it is not.

train_qa.py — add under LEARNING_RATE
# ---------------------------------------------------------------
# SESSION 4, CHANGE 1: the red pen only marks the answer.
# Count how many <|assistant|> tags have gone past, and how many
# <|endoftext|> tags. If more replies have STARTED than have
# ENDED, we are inside a reply.
# ---------------------------------------------------------------
ASSISTANT = stoi["<|assistant|>"]
END = stoi["<|endoftext|>"]

replies_started = torch.cumsum((data == ASSISTANT).int(), 0)
replies_ended = torch.cumsum((data == END).int(), 0)
# Count the ends BEFORE each token, not up to it, so the <|endoftext|>
# tag itself is still graded. The model has to learn when to stop.
replies_ended = torch.cat([torch.zeros(1, dtype=replies_ended.dtype), replies_ended[:-1]])

answer_mask = (replies_started > replies_ended) & (data != ASSISTANT)

Match each line to the picture. data == ASSISTANT puts a 1 wherever an <|assistant|> tag is and a 0 everywhere else. torch.cumsum is a running total: it adds those up as it goes, so replies_started is the "replies started" row of numbers. The same two lines on END give the "replies ended" row. The torch.cat line shifts that row one place to the right, so each piece sees the ends that came before it, which is what keeps the <|endoftext|> tag graded. The last line is the light switch: on when started is bigger than ended, except on the <|assistant|> tag itself. Here is the same thing as a table:

🔨 Activity 2: Use the list in the loss

Two edits. First, the list has to live in the same place as the book (on the GPU, if there is one). Find the line that moves data and add the list under it:

train_qa.py — OLD, then NEW
data = data.to(device)

Second, the loss itself. Inside the training loop, find these lines:

train_qa.py — the OLD lines, inside the loop
    y = torch.stack([data[i + 1:i + block_size + 1] for i in ix])

    logits = model(x)
    loss = F.cross_entropy(logits.view(-1, vocab_size), y.view(-1))

Replace them with this. The True/False values for each chunk are cut out of the list exactly the way y is cut out of the book, so every word piece lines up with its own True or False:

train_qa.py — the NEW lines
    y = torch.stack([data[i + 1:i + block_size + 1] for i in ix])
    graded = torch.stack([answer_mask[i + 1:i + block_size + 1] for i in ix]).float()

    logits = model(x)
    # One mark per token, as before - but now only the answer tokens count.
    every_token = F.cross_entropy(logits.view(-1, vocab_size), y.view(-1),
                                  reduction="none").view(batch_size, block_size)
    loss = (every_token * graded).sum() / graded.sum()

What it does, line by line. reduction="none" asks for one red-pen mark per word piece instead of the average. Multiplying by graded turns every mark outside a reply into zero, because False counts as 0 and True counts as 1. Dividing by graded.sum() averages over the reply pieces only. That is the whole change.

Try it with eight word pieces Pretend one tiny chunk has eight pieces and the red pen gave these marks. Multiply each mark by its True/False (1 or 0), add up what is left, and divide by how many were graded.

The printed loss is now an answer loss. It will not match Session 3's 1.718, because that number included the easy topic lines and tags, which pulled the average down. v6's answer loss, measured the new way, is about 1.8. That is your starting line.

4. A Fair Test

In one sentence To compare two models fairly, give them exactly the same test and take the luck out.

Why "ask it five questions" is not enough any more

Last session you compared v5 and v6 by asking both five questions and judging by eye. That worked because the difference was huge. Today's difference is smaller, and the dice make it hard to see: ask v6 the same question twice and you get two different answers. Which one do you write down?

Two fixes, both written for you:

  • No dice. The new talk_to_your_engine.py always picks the model's favourite word piece (TEMPERATURE = 0.0). Same question, same answer, every time. That is fair.
  • A number. test_session4.py cuts the same 300 chunks from the book for every model and reports the answer loss: how surprised the model was by the tutor's real replies. Lower is better, and luck has nothing to do with it.
Unfair against fair
An unfair test
Ask v6 a question. Ask v7 a different question. The dice are on, so each model would give a different answer if you asked again. Decide by eye which answer "felt better". Two people doing this would disagree.
A fair test
Cut the same 300 chunks of the book for both models. Dice off, so the result is the same every time you run it. Score each model on how surprised it was by the tutor's real replies, and get one number each. Anyone who runs it gets the same two numbers.

Like comparing two runners: same track, same distance, same day. Not one running uphill in the wind and the other on a treadmill.

What happened to Session 2's four dials?

We tested them on v6. The repetition penalty, which rescued the tiny one-layer model from loops, now makes a six-layer model worse. It stops the model reusing words it actually needs, so "photosynthesis" turns into "the process that happens during photosynthesis... through respiration". Temperature and top-k neither helped nor hurt.

The lesson: a fix that worked on a small model is not automatically right for a bigger one. Measure again. For today, the dials are off.

Check yourself: why is "lower answer loss" a fairer way to compare v6 and v7 than "which gave the better answer to my question"?

The answer loss averages over thousands of word pieces in 300 chunks, and the dice are off, so it comes out the same every time. One chat answer is a single roll of the dice on a single question. v7 can lose one question to v6 and still be the better model overall, which is why the five chat questions are a sanity check and the number is the result.

⚙ Troubleshooting & FAQs

Graded : 0% of them

Every word piece was marked False. Usually the comparison is backwards (< instead of >), or replies_ended was shifted the wrong way. Compare your three mask lines with Activity 1 character by character.

RuntimeError: Expected all tensors to be on the same device

The book went to the GPU and the list did not, or the other way round. Both .to(device) lines from Activity 2 must be there, next to each other.

RuntimeError: Error(s) in loading state_dict when it starts from v6

Your attention_engine.py is not the Session 3 shape. Run Session 3's Activity 4 count: it must say 7,951,872. Until it does, neither v6 nor v7 will load.

The loss printed in the first 500 steps is higher than 1.81

Normal for a few hundred steps. The optimiser starts fresh and takes a moment to settle onto a model that is already trained. By step 1,000 it should be below where it started. If it is still climbing at step 2,000, the learning rate is too high: check it is 5e-4.

test_session4.py says it cannot find qa_model_v7.pth

It looks in its own folder, then in the project root. The download has to land in one of those two, with exactly that name. Your own two-step file is called my_qa_model_v7.pth, which is a different file.

v7 got a question wrong that v6 got right

It happens, and it is worth writing down. The answer loss is an average over thousands of word pieces. One question can go either way. That is why the number is in the table and the five questions are a sanity check, not the other way round.
