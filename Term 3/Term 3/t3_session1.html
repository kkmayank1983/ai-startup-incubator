1. First, Listen To It — Five Times

Run talk_to_your_engine.py and ask your Session 8 model the same question five times in a row. Not once. Five times.

Why five?

Your model does not have "an answer". At every piece it rolls a dice over all 1,024 options and takes whatever comes up. Ask it once and you have learned nothing — you have seen one roll. Ask it five times and you start to see what it actually does. This is how you will judge every change you make for the rest of the term.

      2.3  Move it to the GPU

      A GPU does thousands of small sums at the same time; a CPU does a handful at a time. Our maths is thousands of small sums, so this is the machine we want. But PyTorch will not move anything for you — you have to say where every piece lives, and if you miss one it stops with an error.

      🛠 Activity 3: Tell PyTorch where things live

      Four small edits across two files. Do them in order.

      Step 1: Add the device setting (attention_engine.py)

      • Stay in attention_engine.py, in the same settings block you just edited.
      • Directly under the n_head = 4 line, leave a blank line and add these four lines:
      attention_engine.py — add UNDER the n_head line
      n_head = 4         # how many heads of attention the AI has

# Where the maths happens. A GPU does thousands of small sums at the same
# time; a CPU does a few at a time. Same code, same model, same answers -
# it just gets there faster.
device = "cuda" if torch.cuda.is_available() else "cpu"

      Step 2: Build the position numbers on the right machine (attention_engine.py)

      • Scroll down to class PredictionEngine, then to its forward method.
      • Find the line with the comment # where does it sit? on the end — it currently reads pos_emb = self.position_embedding_table(torch.arange(T)).
      • Replace that one line with these four. The only real change is adding device=idx.device inside torch.arange:
      attention_engine.py — inside PredictionEngine.forward
              tok_emb = self.token_embedding_table(idx)   # what is this token?

        # arange has to be built on the SAME machine the model lives on,
        # or PyTorch refuses to add the two together.
        pos_emb = self.position_embedding_table(
            torch.arange(T, device=idx.device))     # where does it sit?

        x = tok_emb + pos_emb                       # combine both cards

      Step 3: Send the model across (attention_engine.py)

      • Go to the very last line of attention_engine.py. It reads model = PredictionEngine(vocab_size).
      • Add .to(device) on the end of it:
      attention_engine.py — the last line of the file
      model = PredictionEngine(vocab_size).to(device)

      Step 4: Send the book across too (train_qa.py)

      • Open train_qa.py.
      • Near the top is the line that imports from your engine. Add , device to the end of it, so the training file knows which machine to use:
      train_qa.py — the import line, near the top
      from attention_engine import model, block_size, batch_size, device
      • Now scroll down to the print(f"Model params : ...") line. Directly under it, add these four lines:
      train_qa.py — add UNDER the "Model params" print

      Step 5: Send the test question across (train_qa.py)

      • Still in train_qa.py, go near the bottom to the block under the comment # --- Ask it something straight away ---.
      • Find the line starting out = model.generate( and add , device=device inside the torch.tensor(...) part:
      train_qa.py — near the bottom

      Check yourself before running. The word device should now appear three times in attention_engine.py and four times in train_qa.py. If your count is short, you have missed a step.

      The error you will probably hit

      RuntimeError: Expected all tensors to be on the same device is the most common GPU message there is, and it means exactly what it says: two things you are adding together live on different machines. Find the one you forgot to move. It is almost always the torch.arange in step 2, or a question tensor you built without device=device.

      At block_size = 64, nine out of ten training examples were being chopped in half. The model almost never saw a question and its complete answer together — so it never learned what a finished answer looks like. At 256, every single block in the book fits, with room to spare.

      How to pick a window size

      Not "the book got bigger, so make it bigger." The rule is: the window must hold one complete example, start to finish. Measure your longest example, then pick the next size up. Ours is 241 pieces, so 256.

      5.3  The box of pieces

      Your tokenizer learned 1,024 pieces from the little book. The new book is 195 times larger and has far more distinct physics vocabulary in it — so the same 1,024 pieces would chop every long word into crumbs.

      VOCAB_SIZEWhat happens to gravitationalBook becomes
      1,024chopped into many small crumbsmore tokens
      4,096survives as one or two pieces7,689,481 tokens

      Bigger pieces mean more meaning per slot in the window. A 256-token window holding 4,096-sized pieces sees far more text than one holding 1,024-sized crumbs. The window change and the vocabulary change work together — that is why we do both at once.

      Need Help? View Solutions & Explanation

      Standard Task — what to expect

      The loss number will look lower at 64, and that is a trap. A shorter window is an easier test — guessing the next piece when you can only see 64 back is a different exam from guessing it when you can see 256. You cannot compare the two numbers directly, exactly like the word-versus-piece loss comparison in Session 8. Judge it by the answers, not the loss: at 64 they get shorter and stop mid-thought, because the model never once saw a complete answer while learning.

      Advanced Task — the trade

      A bigger box means longer pieces, so the book becomes fewer tokens and long words survive whole — but the tokenizer takes much longer to learn, and each rare piece is seen fewer times, so it is learned worse. A smaller box chops everything finer: every piece is very well practised, but your 256-token window now holds less actual text. There is no free lunch. Real labs pick this by experiment, which is exactly what you just did.

      Engineering Takeaway

      Every number in a model is a trade, and the only way to know where the line sits is to measure. "It felt better" is not an answer. "91.9% of blocks were being cut off" is.

      Did You Know?

      The window has a name in the industry: the context length. GPT-2 shipped with 1,024. GPT-3 had 2,048. Today's biggest models advertise 200,000 or more — and the reason it is a headline feature is exactly what you saw today: a model can only learn from what fits in the window at once. Your 64 → 256 change is the same move, on the same reasoning, that every lab has made.

      ⚙ Troubleshooting & FAQs
      ❓ RuntimeError: Expected all tensors to be on the same device

      Two things you are combining live on different machines. Check three places: torch.arange(T, device=idx.device) inside forward, data = data.to(device) in train_qa.py, and the question tensor you build before calling generate — it needs device=device too.

      ❓ RuntimeError: size mismatch … loading qa_model_v3.pth

      Last term's model was built for 1,024 pieces and a 64-token window. Today's engine builds itself for 4,096 and 256. The old weights will never fit the new engine — load qa_model_v4.pth instead.

      ❓ It says "Running on: cpu" in Colab

      The runtime is not set to GPU. Go to Runtime → Change runtime type → T4 GPU, then run the cell again. Everything will still work on CPU — it will just take about 36 minutes instead of 1.4.

      ❓ It sits there for 3–4 minutes before printing anything

      That is the tokenizer re-learning all 4,096 glue rules from the 36 MB book, every single time data_pipeline.py is imported — we still never saved them to a file. It was 15 seconds on the little book; on this one it is minutes. Saving the rules once is a very good stretch task.

      ❓ My loss is different from 2.013

      Expected, and fine. A different GPU, a different PyTorch version, or any change to the seed will move it. What should match is the shape: starting near 3.9 and falling steadily to around 2. If it is stuck above 3 after 2,000 steps, check that your input.txt really is the 36 MB file.
